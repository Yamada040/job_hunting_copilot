# リリースとロールバック

本番リリースは `dev` から `master` へのリリースPRだけで行う。`master` にマージすると、GitHub Actions が次の順に実行する。

1. 本番Supabaseへマイグレーションを適用する。
2. Vercelへ本番デプロイする。
3. `https://job-seeker-gray.vercel.app/v1/health` を最大30秒・3回の再試行で確認する。
4. 成功時は日付タグとGitHub Releaseを作る。失敗時はGitHub Issueを作り、実行ログへのリンクを残す。

## リリース前

1. `dev` を最新化し、必要なCIが通っていることを確認する。
2. マイグレーションを含む場合は、リリースPRの `migrations` ジョブのSummaryで対象SQLを確認する。
3. マイグレーションは、直前のコードでも動く前方互換なものだけにする。列の削除は次のリリースまで分ける。

## リリース後の確認

1. Releaseワークフローのヘルスチェックが成功したことを確認する。
2. 本番でログイン、主要な一覧の表示、データの作成・更新を確認する。
3. GitHub Releaseとタグが作られたことを確認する。

## ロールバック

障害時は、まずVercel Dashboardで直前の正常な本番デプロイを確認し、Instant Rollbackを行う。DBマイグレーションはロールバックしない。前方互換を守るため、直前のコードが新しいスキーマでも動く前提である。

Vercel HobbyではInstant Rollbackで戻せる候補が直前のデプロイに限られることがある。また、ロールバック後は本番ドメインの自動割り当てが外れ、次の `vercel deploy --prod` が本番へ反映されない可能性がある。ロールバック後は、Vercel Dashboardで本番ドメインが目的のデプロイを向いていることを必ず確認する。

データ破損や互換性がないマイグレーションが原因なら、コードのロールバックだけでは復旧しない。DBバックアップからの復旧手順を先に確認し、データへの操作は別途判断する。
